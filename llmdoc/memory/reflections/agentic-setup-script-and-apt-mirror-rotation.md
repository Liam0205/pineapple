# 评审器环境准备脚本接入 + apt 镜像轮转修复复盘

日期：2026-08-08。分支 `feat/pr-review-setup-script`，接在 PR #194（issue #193）合入之后。

起因：PR #194 的评审 bot 在结论里如实写了它没能跑完的检查——runner 缺 `ruff` 与 `golangci-lint`、JDK 版本低于 `pom.xml` 要求的目标版本 25（属性名是 `maven.compiler.source`/`target`，不是 `release`）、因此 `make lint` 与 Java 测试都没执行完。上游 `agentic-workflow-template` PR #30 刚好加了 `setup_script` 扩展点，于是本次把它接上。

## 一、最重要的一条：读脚本看不出来的缺陷，跑一次就暴露

本次写的 `.github/agentic/setup.sh` 有两个缺陷，**都不是靠审读发现的，是靠真跑一遍发现的**，而且两个的症状完全一样、都极具欺骗性——"报告所有能力都不可用，实际什么都没装"，日志读起来像是"环境确实不支持"，而不像"脚本自己坏了"。

1. **`timeout` 是外部程序，调不了 shell 函数。** `timeout 30s setup_java` 里 `setup_java` 是 shell 函数，`timeout` 作为独立二进制根本看不见它，每个阶段以 `rc=127` 结束。修法是 `export -f` 后在 `bash -c` 里跑。
2. **仓库根目录不能从 `BASH_SOURCE` 推。** 上游 hook 的调用形式是 `cd "$repo_dir" && bash "$hook"`，而 `$hook` 在 `.trusted-base`——一个只含这一个脚本的 sparse checkout。按脚本位置推导根目录，每个阶段都会找不到 `pine-go/go.mod`。

两条的共性：**失败模式伪装成了环境的正常降级**。因为脚本被刻意设计成"失败不致命、把缺失能力报告给 agent"，一个坏掉的脚本和一个诚实报告受限环境的脚本，输出长得一模一样。这类"降级路径掩盖自身缺陷"的结构，必须有一次真实执行来区分，不能靠读。现已加 cwd 的三 marker 断言，让第 2 类问题以一条明确错误立刻失败，而不是伪装成五个阶段各自失败。

配套做法值得保留：用上游**真实的** `run-setup-hook.sh`（`gh api` 拉下来）在本地完整模拟一遍，而不是模拟"我以为 hook 会怎么做"。工作树洁净断言也是这样验证的——写一个 `touch ./stray` 的变体脚本，确认 hook 真的以 exit 1 失败（红），再确认真脚本通过（绿）。这就是 `ci-quality-baseline.md` 里 mutation 验证那条纪律在 CI 配置上的应用；三步配方已写进该 guide 的「验证这个脚本的手工配方」节。

## 二、写下来的"会自愈"如果没实测，就是一句许愿

`ci-apt-install.sh` 是 #125/#164 两次慢镜像事故的产物。它的注释和 `ci-quality-baseline.md` 都写着「mirror rotation 通常会自愈」，本次读 `apt-transport-mirror(1)` 才发现**重试从来没有换过镜像**：

- runner 的 `sources.list` 指向 `mirror+file:/etc/apt/apt-mirrors.txt`；
- 手册明确：只有取用**失败**才 failover 到下一个镜像，且镜像按 `priority:` 升序尝试；
- #164 的失败形式是「镜像答应了，然后以 26 KB/s 爬」——这不算失败，failover 从不触发；
- 于是三次尝试全部回到同一个 `priority:1` 主机。per-attempt timeout 把「一个慢镜像」变成了「三个慢镜像」。

与 #193「无人可见的属性必然腐烂」同族，但失效方式不同，不要合并：#193 是**没人写下来**这条属性、也没有通道能看见它；本次是**写下来了，写的却是期望而非实测**。「重试后会落到另一个镜像」当时既没实测，也没有任何通道能看见它没发生——一个慢镜像日过去，CI 失败了，看起来正好印证「就是镜像慢」，反而强化了错误认知。

沉淀成纪律（已写进 `ci-quality-baseline.md`）：**凡是声称「某个机制会自愈」的注释，都要能说出它靠哪一条具体行为自愈。** 说不出来的，要么去实测，要么别声称。

## 二·五、同一个认知错误，我在修它的时候又犯了一次

第一版修复**自己踩了它刚刚诊断出来的那个坑**，而且是独立审计查出来的，不是我自己发现的。

我在函数注释里正确地写下「文件里的行序不是 apt 遵循的东西，`priority:` 才是」，然后紧接着**按行序**实现了轮转：awk 按读入顺序建 `uri[1..n]` 再左移一位。当 mirrorlist 的行序与 priority 序不一致时（比如 `A priority:3 / B priority:1 / C priority:2`），apt 首选的是 `B`，轮转之后**首选仍然是 `B`**——这一次轮转什么都没做，恰好是本次修复要消除的那个失效模式。

为什么当时没发现：我的全部验证用例都是拿 runner 真实 mirrorlist 的形状造的，而那份文件的行序**恰好**等于 priority 序（`priority:1/2/3` 顺序书写）。在这个形状上按行序轮转与按 priority 轮转结果完全一样，于是五个用例全绿。这与 #183「fixture 声明顺序恰好已是字典序」是**同一个陷阱的第四次现身**：用例取自现实的那个特例，而特例恰好让两种实现不可区分。

判据（比上一条更具体）：**当你写下「X 才是真正生效的东西，不是 Y」时，立刻检查自己的实现是按 X 还是按 Y 算的**，并专门造一个 X 与 Y 不一致的用例。这个用例不会自然出现在从现实抓来的样本里——现实样本恰好一致才是常态。

修法是先按 apt 的真实排序规则（priority 升序、无 priority 者置末）排序，再对排好序的序列左移。修完后 `A p:3 / B p:1 / C p:2` 的首选走位是 B→C→A→B，混合场景 `A p:2 / B 无 / C p:1` 走位是 C→A→B→C，都与 apt 的实际尝试顺序一致。

## 三、修的时候顺手踩到的两个细节，值得单独记

- **轮转必须重写 `priority:` 数值，不能只调行序**，而且**轮转本身也必须按 priority 序而非行序计算**（后半句是上面第二·五节那个缺陷，两者是同一条认知的两个应用点，缺任何一个都会让轮转在某些形状上失效）。无显式 priority 的镜像排最后——所以「去掉 priority 让它随机」是个错误的简化方向。
- **必须按 tab 字段解析。** 格式是 URI + TAB + metadata（metadata 内部可用 tab 或空格分隔）。第一版把整行当字符串做 `sub()`，结果 `arch:amd64` 这类 metadata 被空格连回 URI，apt 会把空格算进 URI。这一条是**变异测试查出来的**：runner 当前的 mirrorlist 只有 `priority:` 一种 metadata，所以真实环境不会触发，属于潜伏损坏。造了「带 arch:」「URL 路径里含字面量 `priority:9`」「单镜像」「纯注释」「不可读」五个用例才钉住。

## 四、预算算术要算，不要估

pine-cpp 阶段给 600s。apt 按默认参数跑，update 与 install 各一轮，最坏值远超这个数——**apt 一个人就能吃掉整个阶段预算，cmake 永远轮不到**。只压小 `ATTEMPT_TIMEOUT` 解决不了，正确修法是**整体包一层 `timeout` 限制 apt 总时长**，再把参数调到「两轮最坏值 ≤ 这层上限」为止。

这个数我算错了三次（见第七·七节），所以现在不在文档里复述具体数值，一律以 `.github/agentic/setup.sh` 里那段把每一项都列出来的注释为准。

构建所需时间是实测的，不是估的：本地 configure 9s（含 clone ~70 MB 的 rapidjson + doctest）、`-j4` 构建测试目标 35s。有了这个数才敢说 300s 留给构建是宽裕的。这与 `reflections/sanitized-fuzz-time-budget-graceful-stop.md` 那条"预算标定要用实测 worst 而非快日均值"同源。

`-j` 并发也按仓库既有纪律封了顶（12），因为这个脚本也能在本地跑，裸 `-j$(nproc)` 在大开发机上是禁止的。

## 五、一条反直觉的时序，别改回去

`pr-review` 从 **PR base commit** 读 setup 脚本。所以**引入它的那个 PR 自己享受不到**——脚本在 base（master）上还不存在，走的是"声明了但可信来源里没有"的分支，降级为一条 warning。已对着真 hook 验证过这条路径。收益从下一个 PR 开始。`update-llmdoc` 从事件固定的 checkout 读，没有这个滞后。

这件事本身没问题（上游是有意如此，为了让当前 PR 无法改写准备脚本），但如果不预先知道，很容易在本 PR 的评审结论里再看到一次"缺 ruff / golangci-lint"，然后误以为接线失败、去改本来正确的代码。

## 六、做对了、可作正面对照的地方

- 版本钉的是 **CI 实际解析出来的值**，不是配置文件的字面写法：`golangci-lint-action@v9` 实际装的是 v2.12.2、`setup-python` 的 `"3.13"` 实际解析成 3.13.14。都去 PR #194 那次运行的日志里核过。照抄配置写法会得到一个"看起来钉了版本、其实和 CI 不同"的脚本。
- 阶段按最便宜在前排序、各自限时，于是一个病态阶段只损失它自己那项能力。pine-cpp 排最后不是因为它不重要，而是因为它是唯一一个历史上真的因为基础设施（而非代码）弄挂过 CI 的步骤。
- 上游文档、上游脚本、runner image 的 manifest 都是直接 `gh api` 拉原文读的，包括 mirrorlist 是怎么配出来的（`configure-apt-sources.sh`）、镜像清单里有哪三个 host。三个 host 是否都提供完整 noble archive 也实测确认了（否则轮转可能落到一个部分镜像上）。

## 七、独立审计查出 9 项，全部为真，其中三项是"注释与代码不符"

盲审（0 阻塞 / 4 重要 / 5 小）9 项全部独立复现确认为真，无误报。分布值得记：

- **1 项是真功能缺陷**：轮转按行序算（第二·五节）。
- **3 项是"写下来的与代码做的不符"**：`rc=124` 才算超时（`--kill-after` 升级为 KILL 时是 137，实测确认，会把"预算耗尽"误报成"脚本坏了"——正好抹掉本次改动自陈要保住的那条区分）；注释说注释与 metadata "preserved verbatim"，实际位置被移到文件开头、metadata 分隔符被归一化；`doc-gaps.md` 说手工配方"已写进 guide"，实际 guide 里只有一半（缺 `gh api` 拉上游 hook 那步）。最后这一项尤其值得记：**它违反的正是本仓库既有的「「由 X 保证」类断言必须能追到具体落点」纪律**，而我在同一次任务里刚引用过那条纪律。
- **2 项是守卫选错判据**：`[[ -s "$tmp" ]]` 防的是"文件为空"，真正要防的是"没有镜像行"（纯注释文件能通过）；`cmake --version` 后面没有 `|| return 1`，断言写了但没有牙。
- **1 项是不原子的写**：`sudo cp` 原地覆盖会先 truncate，中途失败会留下半写的 mirrorlist，且没有原始文件备份。改为 `cp` 到 `.new` + `mv` 原子替换，并 `cp -n` 留一份 `.orig`。
- **1 项是正则过严**：`go 1.26`（无 patch）解析不出来，当前 `go.mod` 是 `go 1.26.2` 所以不触发。
- **1 项是最锋利的**：各阶段预算之和大于 hook 默认上限（数值以 `.github/agentic/setup.sh` 的 `phase` 调用为准），真撞上限时整个进程组被杀，**点名清单那段根本不会执行**——而 guide 里把点名清单称作"agent 唯一能知道缺哪项能力的信号"。也就是说在最需要点名的路径上，这个信号恰好缺席。修法是脚本自己维护总 deadline（读 `SETUP_HOOK_TIMEOUT`、留一小段余量），预算不足时裁剪或跳过后续阶段，保证汇总在所有路径上都被执行到。

## 七·五、修复引入的阻塞缺陷：原子替换丢了权限位，让轮转只能生效一次

第二轮审计给了 1 阻塞。**修 F4（原子替换）的那段代码，把 F1（轮转真的换镜像）的收益又抹掉了。**

`sudo cp "$tmp" "$X"` 覆盖已存在文件时，`cp` 保留目标原有 mode（644）。改成 `cp` 到 `$X.new` 再 `mv` 之后，`.new` 是**新建**文件、继承 `mktemp` 的 600，`mv` 把这个 inode 顶上去。脚本以非 root 运行（全靠 `sudo` 写），于是**第二次** `rotate_mirrorlist` 在函数第一行 `[[ -r "$APT_MIRRORLIST" ]]` 就返回 1，落进 "mirrorlist not rotatable" 分支——轮转从"每次重试都换镜像"退化成"只换一次"，而 `setup.sh` 里"3 attempts 保留两次轮转"那句注释因此变成假命题。

为什么我的用例没抓到：**我每个用例都只调用一次 `rotate_mirrorlist`**。单次调用永远看不见"第一次调用改变了后续调用的前提"这类缺陷。这与第二·五节是同一族的取样盲区，只是轴不同：那次是"输入形状恰好让两种实现等价"，这次是"调用次数恰好不足以暴露状态污染"。

判据：**改动一个会被反复调用的函数时，用例必须至少调用两次**，并断言第二次与第一次同样成功。修法是 `sudo install -m "$(stat -c %a ...)"` 显式钉住 mode；现已验证三次连续轮转 mode 恒为 644、首选镜像走位 B→C→A。

同轮还纠正了我一处**归因错误**：rc=137 的注释我写的是"cmake 的编译子进程扇出和 pip 解包会产生"，审计复现不出来，实测确认——普通超时（含 fork 一大片子进程）一律 124，137 只来自 TERM 被屏蔽或**外部** SIGKILL（CI 上主要是 OOM）。也就是说我把"环境真的坏了"这一类误并进了"预算耗尽"。现改为 137 单独一条分支、文案说明两种可能且不假装能区分。教训：**"实测确认"记的必须是那条具体行为，不能是结论**——我当时确实实测了 137 的存在，但没实测"是什么导致的 137"，却按后者写了注释。

## 七·六、同一个解析函数被审计连续三轮各查出一个缺陷

`hook_budget_seconds`（解析可被覆盖的 `SETUP_HOOK_TIMEOUT`）这一个十行函数，三轮审计各查出一个，且每次都是我"以为已经收口"之后：

1. **第一版**：`case` 里 `*s)` 排在非数字守卫之前，`bogus` 被剥成 `bogu` 喂进算术。这个是我自己的测试当场抓到的。
2. **第二版**（改成 `*[0-9]m` / `*[0-9]s` 匹配数字后缀）：审计指出只看后缀不够——`13m30s`、`1e3s` 都以合法单位结尾却留下非数字残余，前者让 `DEADLINE` 在 `set -u` 下 unbound、**脚本在第一个阶段之前就死掉、点名清单一行不打**；`0.5m`、`abc5m` 让 `DEADLINE=-45`、五阶段全跳过，输出与"诚实报告受限环境"完全一致。改成先剥单位再要求剩余部分整体是数字。
3. **第三版**（`+([0-9])` 整体校验）：审计指出 `+([0-9])` **接受前导零，而 bash 算术把前导零读成八进制**——`010m` 静默算成 480s 而非 600s，`0900s` 直接 `value too great for base` 把整个脚本带走。改为三个分支一律 `10#` 强制十进制。

4. **第四版**（`10#` 强制十进制）：审计指出 `10#` 定住了进制却没定住量级——`999999999999999999m` 乘 60 后整数回绕成一个**正**的巨大值，脚本于是认为预算充足、一个阶段都不裁剪，正是这套机制声称要防的结果（回绕成负数那一支被 `DEADLINE <= 10` 守卫接住，是安全的）。改为算术前先限制位数。

教训不止"先枚举畸形输入"那一条，更具体的是两条：**校验"是数字"和"按十进制解读"是两件独立的事**（`[[ $x == +([0-9]) ]]` 通过不代表 `$(( x ))` 给你期望的值），以及**定住进制之后还要定住量级**（`10#` 不防溢出）。

5. **第五版**（给 `ci-apt-install.sh` 也加 `10#`）：final 审计指出**我只搬了一半纪律**——`setup.sh` 三个分支都加了位数上限，同一次改动里 `ci-apt-install.sh` 的两个同类点却只做了 `10#`。后果比不改更糟：`ATTEMPTS=9223372036854775808` 回绕成负数、`seq 1 <负数>` 产出空序列，于是**apt 一次都不执行**；而不做 `10#` 时这个值本来能正常跑。「归一化反而让情况变坏」是这轮最值得记的一句。现在两个变量都是位数上限 + 越界回落默认值，并且 `ATTEMPTS < 1` 也回落（零次尝试永远不是调用方的意思）。

这条尤其讽刺：`ci-quality-baseline.md` 里那第 4 条纪律（「写下普适纪律时立刻 grep 本次改动范围内所有同类点」）就是我上一轮**自己刚写下的**，然后我在写下它的同一次提交里违反了它。第二次同型（第一次是「说已写进 guide、实际只在 reflection 里」犯两遍）。判据只能更机械：**写完一条纪律，立刻把它当 checklist 逐个 grep，不要相信「我刚想过这件事所以应该都覆盖了」。**

还有一条边界要写清楚，因为我上一版把它写成了普适声明而它并不普适：「凡是喂进 bash 算术的地方都要 `10#`」这句话本身对，但我当时**没有回头检查同一次改动里的另一个脚本**。审计实测 `ATTEMPTS=09` 会让 `ci-apt-install.sh` 的 `[[ "$attempt" -lt "$ATTEMPTS" ]]` 报 "value too great for base" 恒假、**静默关掉镜像轮转**——即写下普适纪律的那次提交自己就违反了它。已一并修掉。判据：**写下"凡是 X 都要 Y"时，立刻 grep 本次改动范围内所有的 X**。

另一个观察：这个函数每一轮都"看起来已经对了"，因为每一版都修掉了上一版被指出的那个具体形状。真正让它收敛的不是修得更细，而是**换了判据的层次**——从"枚举我想到的坏输入"变成"先整体校验合法性、再规定解读进制"。

## 七·七、同一个时间预算算错三次，每次错法不同

apt 外层总预算这一个数，审计连续三轮各查出一次错，而且**每次的错误形式都长得像一份正经算术**——这是它能连续骗过我三次的原因：

1. **拿默认参数算，用来论证实际参数**：算出「默认 3 次 × 300s 两轮 ≈ 1900s」是对的，但我用这个数去论证「300s 够用于我实际传入的 `ATTEMPTS=3 ATTEMPT_TIMEOUT=90`」。而后者两轮最坏是 600s，300s 只覆盖一半。
2. **漏项**：改成 60s/420s 时，我只数了「尝试次数 × 单次超时 + backoff」，漏掉尝试之间的两项——`dpkg --configure -a` 修复（当时**完全没有 `timeout`**、无界）和 mirrorlist 轮转。
3. **补全后发现根本装不下**：把所有项算齐是 798s，而阶段上限只有 600s。这时正确做法不是挑一个数字再声称它覆盖，而是**把参数压到算术真的闭合为止**（现为 3 次 × 40s、dpkg 修复限 30s，两轮最坏 508s ≤ 510s 上限，剩 90s 给 cmake 而 cmake 实测只需 ~44s）。

同轮还查出一个与之相扣的缺陷：per-attempt 的 `timeout` **没有 `--kill-after`**。plain `timeout` 发完 TERM 就无限等待，子进程屏蔽 TERM 时能跑到远超上限**却仍然返回 rc=124**——一个看起来被强制、实际没有的上限。实测 `timeout 3` 下跑满 12s 仍报 124。而脚本注释里预期的 dpkg 持锁场景正是这种情况。这也解释了为什么漏项 2 那么致命：无界的修复步骤 + 假的 per-attempt 上限，两者叠加时总预算完全失控。

判据（已写进 `ci-quality-baseline.md`）：**任何「这个上限覆盖最坏情况」的注释，都要能把被求和的每一项逐条列出来**；列不全就说明还没真算过。以及：**只在尝试之间执行的步骤也要有自己的上限并计入总和**。
